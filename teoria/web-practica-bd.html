CRUD con persistencia real, paso a paso

0/14 pasos
Horas de práctica de laboratorio · Mismo ejercicio, con datos reales

Persistencia en base de datos relacional con ORM y despliegue en Render

Esta guía toma el mismo ejercicio de la práctica anterior (CRUD de Productos) y reemplaza el arreglo en memoria por una base de datos PostgreSQL real, accedida a través de TypeORM (el ORM oficial recomendado por NestJS). Al final desplegarás la API completa, con su base de datos, en Render.

~3 h laboratorio Nivel: intermedio NestJS + TypeORM + PostgreSQL Despliegue en Render
Regla de esta guía: sigue los pasos en orden, sin saltarte ninguno. Cada paso tiene una casilla de Verificación — el botón "Marcar paso completado" solo se activa cuando confirmas que la verificación se cumplió. La prueba más importante de todas está en el Paso 8: vas a reiniciar el servidor y comprobar que los datos siguen ahí. Esa es la diferencia real entre esta práctica y la anterior.
Nota: esta guía asume que ya completaste (o al menos conoces) el CRUD en memoria de web-practica.html — reutilizamos el mismo dominio (Productos), el mismo contrato de URIs y los mismos DTOs de validación. Si no la hiciste, el Paso 1 te deja crear el proyecto base desde cero igualmente.
Paso 0

Verificar el entorno de trabajo

Esta guía asume que no tienes nada instalado todavía para la parte de base de datos, ni falta te hace: vamos a levantar PostgreSQL dentro de un contenedor de Docker, así que no vas a instalar el motor de base de datos directamente en tu sistema operativo.

  1. Abre una terminal y confirma Node y npm (si te faltan, instala Node LTS desde nodejs.org primero):
terminal
$ node --version
# v18.19.0 o superior
$ npm --version
  1. Prepara una carpeta de tu propio usuario para los paquetes globales de npm (evita instalar en /usr/local, que en macOS suele pertenecer a otro dueño y provoca el error EACCES: permission denied al hacer npm i -g):
terminal
$ mkdir -p ~/.npm-global
$ npm config set prefix '~/.npm-global'
$ echo 'export PATH=~/.npm-global/bin:$PATH' >> ~/.zshrc
$ source ~/.zshrc
# en Windows (PowerShell) omite este paso: normalmente no da problemas de permisos
  1. Instala el CLI de Nest de forma global (una sola vez) y confirma:
terminal
$ npm i -g @nestjs/cli
$ nest --version

⚠ Si npm i -g @nestjs/cli te da EACCES: permission denied

Es señal de que el paso 2 de arriba no se aplicó (revisa que npm config get prefix ya no muestre /usr/local) o de que la terminal no recargó tu ~/.zshrc — ciérrala y ábrela de nuevo. Nunca uses sudo npm i -g como atajo: soluciona el síntoma hoy, pero deja la carpeta global con permisos mezclados y provoca errores más raros después.

Instalar Docker Desktop (si nunca lo has usado)

Docker es el programa que va a "contener" PostgreSQL por ti — no vas a instalar Postgres como una aplicación aparte, sino que Docker va a descargar una imagen lista para usar y correrla aislada. Solo necesitas instalar Docker una vez:

  1. Ve a docker.com/products/docker-desktop y descarga el instalador para tu sistema operativo (Windows, Mac con chip Intel/Apple Silicon, o Linux).
  2. Ejecuta el instalador y acepta las opciones por defecto.
    • Windows: el instalador te puede pedir habilitar "WSL2" (Subsistema de Windows para Linux) — acepta y, si te pide reiniciar el computador, hazlo. Es normal que el proceso tome varios minutos e incluya un reinicio.
    • Mac: arrastra la app a la carpeta Aplicaciones como cualquier otra app, y ábrela desde ahí.
  3. Abre la aplicación Docker Desktop (búscala en el menú de inicio o en Spotlight). Espera a que el ícono de la ballena en tu barra de tareas/menú deje de estar "cargando" — Docker Desktop debe quedar abierto y corriendo en segundo plano mientras hagas esta práctica; si lo cierras, los comandos docker dejan de funcionar.
  4. Con Docker Desktop abierto, vuelve a la terminal y confirma:
terminal
$ docker --version
# cualquier versión reciente de Docker Desktop
$ docker run hello-world
# descarga una imagen mínima y, si todo está bien, imprime "Hello from Docker!"

Si docker --version falla con algo como "no se reconoce el comando", Docker Desktop no quedó instalado o no está en el PATH: cierra y vuelve a abrir la terminal, y si sigue fallando, reinstala. Si docker run hello-world falla con "Cannot connect to the Docker daemon", significa que instalaste Docker pero la aplicación Docker Desktop no está abierta — ábrela y espera a que termine de iniciar.

Crea también, si no la tienes, una cuenta gratuita en render.com (puedes registrarte con tu cuenta de GitHub) — la usarás en el Paso 12.

  • node, npm, nest --version y docker --version me responden con un número de versión sin errores.
  • Docker Desktop está abierto y docker run hello-world imprimió "Hello from Docker!".
  • Tengo una cuenta creada en Render (o confirmada si ya la tenía).

Paso 1

Crear (o recuperar) el proyecto base

Si ya tienes nestjs-productos-api de la práctica anterior

Ábrelo en tu editor. Lo vamos a modificar: el arreglo en memoria de ProductosService va a desaparecer por completo y su lugar lo va a ocupar una base de datos real. No necesitas borrar nada todavía, lo iremos reemplazando pieza por pieza en los pasos siguientes.

Si NO lo tienes (empiezas desde cero)

terminal
$ nest new nestjs-productos-api --package-manager npm
$ cd nestjs-productos-api
$ npm i @nestjs/swagger class-validator class-transformer
$ npm run start:dev
# Nest application successfully started, escuchando en http://localhost:3000

Y habilita Swagger + ValidationPipe en src/main.ts (lo ajustaremos otra vez en el Paso 10, así que no te preocupes por el puerto todavía):

src/main.ts
import { NestFactory } from '@nestjs/core';
import { ValidationPipe } from '@nestjs/common';
import { SwaggerModule, DocumentBuilder } from '@nestjs/swagger';
import { AppModule } from './app.module.js';

async function bootstrap() {
  const app = await NestFactory.create(AppModule);

  app.useGlobalPipes(
    new ValidationPipe({
      whitelist: true,
      forbidNonWhitelisted: true,
      transform: true,
    }),
  );

  const config = new DocumentBuilder()
    .setTitle('API de Productos (con persistencia)')
    .setDescription('CRUD de productos sobre PostgreSQL + TypeORM')
    .setVersion('1.0')
    .build();
  const document = SwaggerModule.createDocument(app, config);
  SwaggerModule.setup('swagger', app, document);

  await app.listen(3000);
}
bootstrap();

Paso 2

Levantar PostgreSQL local con Docker

Aquí es donde realmente "instalas" PostgreSQL: no como un programa aparte en tu sistema operativo, sino como una imagen de Docker que se descarga una sola vez y luego corre siempre dentro de un contenedor aislado — igual a como lo tendrás en Render, solo que local. Con Docker Desktop abierto (Paso 0):

  1. Descarga ("instala") la imagen oficial de PostgreSQL versión 16:
terminal
$ docker pull postgres:16
# descarga la imagen desde Docker Hub — puede tardar uno o dos minutos la primera vez
  1. Crea y arranca un contenedor a partir de esa imagen, con usuario, contraseña y base de datos ya configurados:
terminal
$ docker run --name pg-productos \
  -e POSTGRES_USER=postgres \
  -e POSTGRES_PASSWORD=postgres \
  -e POSTGRES_DB=productos_db \
  -p 5432:5432 \
  -d postgres:16
# arranca el contenedor en segundo plano (-d) usando la imagen ya descargada
  1. Confirma que el contenedor está corriendo:
terminal
$ docker ps
# debe aparecer pg-productos con estado "Up"
$ docker exec -it pg-productos psql -U postgres -d productos_db -c "\dt"
# "Did not find any relations." es la respuesta correcta: la BD existe, aún sin tablas

Si necesitas parar o reiniciar el contenedor más adelante: docker stop pg-productos / docker start pg-productos. Los datos persisten mientras no ejecutes docker rm sobre el contenedor.

⚠ Problemas comunes

  • Cannot connect to the Docker daemon: Docker Desktop no está abierto. Ábrelo y espera a que termine de iniciar antes de repetir el comando.
  • port is already allocated en el puerto 5432: ya tienes otro PostgreSQL (o otro contenedor) usando ese puerto. Detén el otro proceso, o cambia este contenedor a otro puerto de tu máquina con -p 5433:5432 (y ajusta el DATABASE_URL del Paso 3 a localhost:5433).
  • Conflict... container name "/pg-productos" is already in use: ya creaste el contenedor antes; no necesitas volver a crearlo, solo arráncalo con docker start pg-productos.
Verificación del Paso 2
  • docker ps muestra pg-productos corriendo.
  • Pude conectarme con psql dentro del contenedor y ver que productos_db existe.
Marca ambas casillas para continuar.
Paso 3

Conectar TypeORM al proyecto

Instala el ORM, el driver de PostgreSQL y el módulo de configuración de variables de entorno:

terminal
$ npm i @nestjs/typeorm typeorm pg @nestjs/config
  1. Crea un archivo .env en la raíz del proyecto (nunca se sube a git):
.env
DATABASE_URL=postgresql://postgres:postgres@localhost:5432/productos_db
NODE_ENV=development
  1. Edita src/app.module.ts para registrar la conexión:
src/app.module.ts
import { Module } from '@nestjs/common';
import { ConfigModule, ConfigService } from '@nestjs/config';
import { TypeOrmModule } from '@nestjs/typeorm';

@Module({
  imports: [
    ConfigModule.forRoot({ isGlobal: true }),
    TypeOrmModule.forRootAsync({
      imports: [ConfigModule],
      inject: [ConfigService],
      useFactory: (config: ConfigService) => ({
        type: 'postgres',
        url: config.get<string>('DATABASE_URL'),
        autoLoadEntities: true,
        // sin migraciones en este proyecto: se sincroniza también en producción
        synchronize: true,
        ssl: config.get('NODE_ENV') === 'production'
          ? { rejectUnauthorized: false }
          : false,
      }),
    }),
  ],
})
export class AppModule {}

⚠ Sobre synchronize

synchronize: true hace que TypeORM cree y ajuste las tablas automáticamente a partir de tus entidades. En un proyecto real no se usa así, porque puede alterar o borrar columnas con datos en producción sin avisar — ahí se usan migraciones (typeorm migration:generate / migration:run). Esta práctica no cubre migraciones, así que lo dejamos activo también en producción (Render); si no, al desplegar la tabla productos nunca se crearía y toda petición fallaría.

  1. Reinicia npm run start:dev. Si la consola arranca sin errores de conexión, TypeORM ya está hablando con Postgres (aunque todavía no exista ninguna entidad).

Paso 4

Generar el módulo de Productos y la Entity

  1. Si aún no existen (o si vienes de la práctica anterior, ya los tienes), genera módulo, controlador y servicio:
terminal
$ nest g module productos
$ nest g controller productos --no-spec
$ nest g service productos --no-spec
  1. Reemplaza (o crea) src/productos/producto.entity.ts — ya no es una clase plana, ahora describe una tabla real:
src/productos/producto.entity.ts
import { Column, Entity, PrimaryGeneratedColumn } from 'typeorm';

@Entity('productos')
export class Producto {
  @PrimaryGeneratedColumn()
  id: number;

  @Column()
  nombre: string;

  @Column('numeric', {
    precision: 10,
    scale: 2,
    transformer: {
      to: (value: number) => value,
      from: (value: string) => parseFloat(value),
    },
  })
  precio: number;
}

Un detalle que sorprende la primera vez

El driver de PostgreSQL devuelve las columnas numeric/decimal como string (para no perder precisión), no como number. Sin el transformer de arriba, precio llegaría como "45.90" en vez de 45.9. El transformer convierte automáticamente en ambas direcciones (guardar/leer).

  1. Edita src/productos/productos.module.ts para registrar la entidad:
productos.module.ts
import { Module } from '@nestjs/common';
import { TypeOrmModule } from '@nestjs/typeorm';
import { Producto } from './producto.entity.js';
import { ProductosController } from './productos.controller.js';
import { ProductosService } from './productos.service.js';

@Module({
  imports: [TypeOrmModule.forFeature([Producto])],
  controllers: [ProductosController],
  providers: [ProductosService],
})
export class ProductosModule {}
  1. Reinicia el servidor y confirma que ahora sí existe la tabla:
terminal
$ docker exec -it pg-productos psql -U postgres -d productos_db -c "\dt"
# ahora debe listar la tabla "productos"

Paso 5

GET (listar / obtener) usando el Repository

TypeORM te da un Repository por entidad — un objeto con métodos (find, findOneBy, save, delete...) que traduce a SQL por ti. Se inyecta con @InjectRepository.

  1. Reemplaza src/productos/productos.service.ts por completo:
productos.service.ts
import { Injectable, NotFoundException } from '@nestjs/common';
import { InjectRepository } from '@nestjs/typeorm';
import { Repository } from 'typeorm';
import { Producto } from './producto.entity.js';

@Injectable()
export class ProductosService {
  constructor(
    @InjectRepository(Producto)
    private readonly productosRepository: Repository<Producto>,
  ) {}

  findAll(): Promise<Producto[]> {
    return this.productosRepository.find();
  }

  async findOne(id: number): Promise<Producto> {
    const producto = await this.productosRepository.findOneBy({ id });
    if (!producto) throw new NotFoundException(`Producto ${id} no existe`);
    return producto;
  }
}
  1. El controlador queda prácticamente igual que en la práctica anterior (Nest maneja las promesas solo):
productos.controller.ts
import { Controller, Get, Param, ParseIntPipe } from '@nestjs/common';
import { ProductosService } from './productos.service.js';

@Controller('api/v1/productos')
export class ProductosController {
  constructor(private readonly productosService: ProductosService) {}

  @Get()
  listar() {
    return this.productosService.findAll();
  }

  @Get(':id')
  obtener(@Param('id', ParseIntPipe) id: number) {
    return this.productosService.findOne(id);
  }
}
  1. Prueba GET /api/v1/productos en Swagger: como la tabla está vacía, debe responder 200 con [] (no un error — una tabla vacía es un resultado válido).
  2. Prueba GET /api/v1/productos/1: debe responder 404, porque aún no existe ninguna fila.
Verificación del Paso 5
  • GET /productos responde 200 con un arreglo vacío [].
  • GET /productos/1 responde 404.
Marca ambas casillas para continuar.
Paso 6

POST (crear) con persistencia real

El DTO de validación no cambia respecto a la práctica anterior — la validación de entrada es independiente de dónde se guarden los datos.

  1. Crea src/productos/dto/crear-producto.dto.ts:
dto/crear-producto.dto.ts
import { IsNotEmpty, IsNumber, IsPositive, IsString } from 'class-validator';

export class CrearProductoDto {
  @IsString()
  @IsNotEmpty()
  nombre: string;

  @IsNumber()
  @IsPositive()
  precio: number;
}
  1. Agrega este método a ProductosService:
productos.service.ts
import { CrearProductoDto } from './dto/crear-producto.dto.js';

// ...dentro de la clase:
async crear(dto: CrearProductoDto): Promise<Producto> {
  const nuevo = this.productosRepository.create(dto);
  return this.productosRepository.save(nuevo);
}

create() arma la instancia en memoria (todavía no toca la base de datos); save() es el que genera el INSERT real y devuelve la fila ya con su id autogenerado por Postgres.

  1. Agrega este método al controlador:
productos.controller.ts
import { Body, Controller, Get, HttpCode, HttpStatus, Param, ParseIntPipe, Post, Res } from '@nestjs/common';
import type { Response } from 'express';
import { CrearProductoDto } from './dto/crear-producto.dto.js';

@Post()
@HttpCode(HttpStatus.CREATED)
async crear(@Body() dto: CrearProductoDto, @Res({ passthrough: true }) res: Response) {
  const nuevo = await this.productosService.crear(dto);
  res.setHeader('Location', `/api/v1/productos/${nuevo.id}`);
  return nuevo;
}
  1. En Swagger, prueba POST /api/v1/productos con { "nombre": "Teclado mecánico", "precio": 45.90 }. Debe responder 201 con header Location.
  2. Ahora ve directo a la base de datos sin pasar por la API y confirma que la fila realmente está ahí:
terminal
$ docker exec -it pg-productos psql -U postgres -d productos_db -c "SELECT * FROM productos;"
# debe mostrar la fila que acabas de crear, con su id, nombre y precio

Repite el POST dos veces más con otros productos, para tener varios registros con los que seguir probando.

Verificación del Paso 6
  • POST válido responde 201 con header Location.
  • Vi la fila creada directamente con SELECT * FROM productos; en psql, no solo en la respuesta de la API.
Marca ambas casillas para continuar.
Paso 7

PUT y PATCH con persistencia real

  1. Crea src/productos/dto/actualizar-precio.dto.ts:
dto/actualizar-precio.dto.ts
import { IsNumber, IsPositive } from 'class-validator';

export class ActualizarPrecioDto {
  @IsNumber()
  @IsPositive()
  precio: number;
}
  1. Agrega estos dos métodos a ProductosService:
productos.service.ts
async reemplazar(id: number, dto: CrearProductoDto): Promise<void> {
  const producto = await this.findOne(id); // lanza 404 si no existe
  await this.productosRepository.save({ ...producto, ...dto });
}

async actualizarPrecio(id: number, dto: ActualizarPrecioDto): Promise<Producto> {
  const producto = await this.findOne(id);
  producto.precio = dto.precio;
  return this.productosRepository.save(producto);
}

Reutilizamos findOne() (que ya lanza NotFoundException) en vez de repetir la búsqueda a mano — así el 404 queda garantizado en un solo lugar.

  1. Agrega estos dos métodos al controlador:
productos.controller.ts
import { Patch, Put } from '@nestjs/common';
import { ActualizarPrecioDto } from './dto/actualizar-precio.dto.js';

@Put(':id')
@HttpCode(HttpStatus.NO_CONTENT)
async reemplazar(@Param('id', ParseIntPipe) id: number, @Body() dto: CrearProductoDto) {
  await this.productosService.reemplazar(id, dto); // 204: sin cuerpo
}

@Patch(':id')
async actualizarPrecio(@Param('id', ParseIntPipe) id: number, @Body() dto: ActualizarPrecioDto) {
  return this.productosService.actualizarPrecio(id, dto); // 200: devolvemos el recurso
}
  1. Prueba PUT /api/v1/productos/1 con un objeto completo: debe responder 204.
  2. Prueba PATCH /api/v1/productos/1 con { "precio": 60.00 }: debe responder 200 con el producto actualizado.
  3. Confirma en psql (SELECT * FROM productos WHERE id = 1;) que el precio realmente cambió en la tabla.
  4. Prueba ambos verbos con id=999: deben responder 404.
Verificación del Paso 7
  • PUT válido responde 204 y PATCH válido responde 200, y el cambio se ve en psql.
  • Ambos responden 404 con un id inexistente.
Marca ambas casillas para continuar.
Paso 8 · El paso clave

DELETE, y comprobar que la persistencia es real

  1. Agrega este método a ProductosService:
productos.service.ts
async eliminar(id: number): Promise<void> {
  const resultado = await this.productosRepository.delete(id);
  if (resultado.affected === 0) {
    throw new NotFoundException(`Producto ${id} no existe`);
  }
}

delete() ejecuta un DELETE SQL directo por id — no necesita cargar la fila primero. resultado.affected te dice cuántas filas realmente se borraron (0 significa que ese id no existía).

  1. Agrega este método al controlador:
productos.controller.ts
import { Delete } from '@nestjs/common';

@Delete(':id')
@HttpCode(HttpStatus.NO_CONTENT)
async eliminar(@Param('id', ParseIntPipe) id: number) {
  await this.productosService.eliminar(id); // 204
}
  1. Ejecuta DELETE /api/v1/productos/2: debe responder 204.
  2. Ejecuta el mismo DELETE una segunda vez: debe responder 404, nunca 500.
La prueba que distingue esta práctica de la anterior
  1. Anota cuántos productos tienes ahora mismo (GET /api/v1/productos).
  2. Detén completamente el servidor de Nest (Ctrl+C en la terminal donde corre npm run start:dev).
  3. Vuelve a ejecutar npm run start:dev desde cero.
  4. Ejecuta GET /api/v1/productos otra vez.

En la práctica anterior (arreglo en memoria), reiniciar el servidor borraba todo y volvías a ver solo los 3 productos iniciales del código. Aquí, tus productos siguen exactamente igual — porque nunca vivieron en la memoria del proceso de Node, sino en Postgres, un proceso completamente aparte.

Verificación del Paso 8
  • El primer DELETE da 204; el segundo, sobre el mismo id, da 404.
  • Reinicié el servidor por completo y mis productos siguen ahí — la persistencia es real.
Marca ambas casillas para continuar.
Paso 9 · Reto

Búsqueda por nombre usando el ORM

Resuelve antes de continuar

Agrega soporte para GET /api/v1/productos?nombre=teclado, que debe devolver solo los productos cuyo nombre contenga ese texto (sin distinguir mayúsculas/minúsculas).

⚠ Reemplaza, no agregues

Los dos bloques de abajo reemplazan por completo el findAll() del Paso 5 (en productos.service.ts) y el listar() del Paso 5 (en productos.controller.ts). Si dejas los dos métodos (el viejo sin parámetro y este nuevo) vas a tener dos funciones con el mismo nombre en la misma clase, y TypeScript falla con Duplicate function implementation. Borra la versión vieja de cada uno antes de pegar la nueva.

productos.service.ts
import { ILike, Repository } from 'typeorm';

findAll(nombre?: string): Promise<Producto[]> {
  if (!nombre) return this.productosRepository.find();
  return this.productosRepository.find({
    where: { nombre: ILike(`%${nombre}%`) },
  });
}
productos.controller.ts
import { Query } from '@nestjs/common';

@Get()
listar(@Query('nombre') nombre?: string) {
  return this.productosService.findAll(nombre);
}

ILike es específico de PostgreSQL (comparación tipo LIKE insensible a mayúsculas). Fíjate que sigues sin escribir SQL a mano — el ORM traduce el operador por ti.

Prueba GET /api/v1/productos?nombre=teclado y confirma que solo devuelve las coincidencias, y que GET /api/v1/productos (sin query) sigue devolviendo todos.

Paso 11

Subir a GitHub y automatizar las pruebas con Actions

  1. Crea un repositorio vacío en github.com/new (sin README, sin .gitignore — ya tienes los tuyos) y copia su URL.
  2. Conecta tu proyecto local y sube el primer commit:
terminal
$ git init
$ git add .
$ git commit -m "feat: CRUD de productos con TypeORM + PostgreSQL"
$ git branch -M main
$ git remote add origin https://github.com/<tu-usuario>/<tu-repo>.git
$ git push -u origin main

⚠ Si git push no refleja tus últimos cambios en GitHub Actions

Confirma que estás en la rama main (git branch) y que el push terminó sin errores (git log origin/main -1 debe mostrar tu último commit). Un push a otra rama, o interrumpido a mitad de camino, deja Actions corriendo sobre código viejo sin avisarte.

  1. Crea la carpeta .github/workflows/ en la raíz del proyecto y dentro el archivo tests.yml:
.github/workflows/tests.yml
name: Tests

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  test:
    runs-on: ubuntu-latest

    services:
      postgres:
        image: postgres:16
        env:
          POSTGRES_USER: postgres
          POSTGRES_PASSWORD: postgres
          POSTGRES_DB: productos_db
        ports:
          - 5432:5432
        options: >-
          --health-cmd "pg_isready -U postgres"
          --health-interval 10s
          --health-timeout 5s
          --health-retries 5

    env:
      DATABASE_URL: postgresql://postgres:postgres@localhost:5432/productos_db
      NODE_ENV: test

    steps:
      - name: Checkout
        uses: actions/checkout@v4

      - name: Setup Node.js
        uses: actions/setup-node@v4
        with:
          node-version: '22'
          cache: 'npm'

      - name: Install dependencies
        run: npm ci

      - name: Build
        run: npm run build

      - name: Unit tests
        run: npm test

      - name: E2E tests
        run: npm run test:e2e

Este workflow levanta su propio contenedor de PostgreSQL (independiente del pg-productos local del Paso 2) solo mientras corren las pruebas — por eso DATABASE_URL aquí es una variable del workflow, no tu .env (que nunca se sube al repo).

⚠ Si Actions falla en "Install dependencies" con npm ci

npm ci exige que package-lock.json esté perfectamente sincronizado con package.json. Si ves un error como Missing: <paquete> from lock file, corre npm install en tu máquina (regenera el lock), y sube ese cambio con un nuevo commit.

  1. Sube el workflow:
terminal
$ git add .github
$ git commit -m "ci: agregar GitHub Actions para pruebas"
$ git push
  1. Ve a la pestaña Actions de tu repositorio en GitHub y espera a que el workflow "Tests" termine — debe quedar con un check ✅ verde. Si queda en rojo ❌, abre el log del paso que falló antes de seguir al Paso 12.

  • La pestaña Actions muestra el workflow "Tests" en verde (✅), no en rojo.

Paso 12

Desplegar en Render

  1. En el dashboard de Render: New → PostgreSQL. Elige un nombre (p. ej. productos-db), la región más cercana y el plan gratuito. Espera a que quede en estado "Available".
  2. Copia la Internal Database URL que Render te muestra (si tu Web Service va a vivir en la misma región, es la más rápida y no consume tu ancho de banda saliente).
  3. En el dashboard: New → Web Service. Conecta el mismo repositorio de GitHub del Paso 11.
  4. Configura el servicio:
Configuración del Web Service en Render
CampoValor
Build Commandnpm install --include=dev && npm run build
Start Commandnpm run start:prod
Variable DATABASE_URLla Internal Database URL copiada en el paso 2
Variable NODE_ENVproduction

⚠ Sobre --include=dev en el Build Command

Render aplica la variable NODE_ENV=production también durante el build, y con eso npm install por defecto omite las devDependencies — ahí vive @nestjs/cli, que provee el comando nest. Sin --include=dev el build falla con sh: 1: nest: not found.

  1. Guarda y despliega. Sigue los logs de build hasta ver Nest application successfully started.
  2. Abre https://<tu-servicio>.onrender.com/swagger y repite ahí la misma matriz de pruebas del Paso 7 de la práctica anterior (POST, GET, PUT, PATCH, DELETE) — ahora contra la base de datos administrada por Render, no tu Postgres local.

⚠ Cold start en el plan gratuito

En el plan gratuito de Render, el servicio "duerme" tras un rato sin tráfico y la primera petición después de eso puede tardar unos 30–60 segundos en responder mientras arranca de nuevo. No es un error tuyo — es el comportamiento esperado del plan gratuito.
